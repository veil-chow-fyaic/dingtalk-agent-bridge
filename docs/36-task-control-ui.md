## 实际发现与修复

第一条 `/agent status` 在空闲时返回 `queued:1`。账本显示状态查询已完成，实际排队数为0。原因是gateway先把查询自身以queued写入，再取summary，最后才改completed。

修复为先完成查询，再取快照；UI回复改成中文说明执行中、排队、等待附件、已完成/取消、历史需处理记录及回复投递状态。summary接口和既有账本不变；保留那条历史blocked，不删失败来变绿。上传未知/发送未知仍在“结果未确认”中显示，不暗示可以重发。

两条新的查询独立验证空闲0/0及真实运行时1/1。同一句 `/agent status` 的三个原生消息ID各处理一次；旧错误回复原样保留，不是重放旧请求或改key掩盖未知结果。

## 用户操作及结果

| 操作 | 真实结果 |
|---|---|
| 空闲状态查询 | 修复前错误queued:1；修复后“执行中0，排队0，等待附件0”，历史需处理1 |
| 可取消任务 | Kimi实际调用Bash→Python执行 `time.sleep(120)`；约定等待结束后才写一个唯一合成文件，等待前不写 |
| 后续任务入队，再查状态 | 第二个任务要求计算19×23；UI显示执行中1、排队1，查询自身未再制造额外排队 |
| `/agent cancel` | UI先显示请求停止，再显示任务已停止；被观察到的Kimi及子进程已消失，原定120秒之后合成输出文件仍不存在 |
| 队列继续 | 后续实际Kimi任务回复“队列继续437”，没有重做已取消任务或生成其文件 |
| 旧会话记忆→`/agent new`→新会话提问 | 旧会话明确记住合成口令；新会话确认可见，generation仅+1且原native binding先清空，再绑定不同会话ID；新回复“新会话无旧口令” |

status/cancel/new控制本身没有调用模型；4个实际runtime任务分别为等待、队列后续、口令种子和新会话验证。新工作区与旧工作区分别保留，群会话及其任务没有被重置。会话隔离不等于OS安全沙箱，取消也不能撤销任务此前已完成的操作。
