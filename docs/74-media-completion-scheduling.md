# 快速附件完成结果不再丢失

2026-11-12，E057。修复同批附件的下载调度竞态：下载在后台很快完成时，下一条消息过去会清空不属于自己的完成结果，再发起自己的下载。两条消息轮流覆盖，可能持续停在等待附件；这是本地调度错误，不是 DWS 投递失败。

确定性复现使用真实本地下载线程，在每次启动返回前等待该线程结束，模拟快速缓存命中。旧源码处理两条消息，三轮 intake 发起六次下载，两条仍未就绪；另一个场景中，已重试消息被二十个新候选挤出窗口，已完成结果无法消费。旧 E054 已安装 wheel 同样复现这两项失败，原日志保留。

## 修改和验证

完成结果现在仅由原消息消费，其他消息不会清空它。Inbox 的有界候选窗口优先处理当前下载的所属消息，随后仍按重试次数和事件顺序选择。若所属任务已取消，完成后的结果会丢弃；正在执行的下载仍占用唯一槽位直到结束或超时，不无限增开线程，也不重新执行取消任务。

四个新增回归验证：两条快速附件各下载/执行一次且完成后重启不重放；二十个新候选前优先消费已有结果；取消后迟到结果不复活任务、后续附件可执行；等待附件时重启保持任务/确认消息身份，重新取得原件后仅执行一次。重启允许重复只读下载，与自动重做有副作用的 Agent 任务分开。

源码 Python3.14 全量 **184 项**，隔离已安装 wheel 在 Python3.14 和最低 Python3.11 各 **184 项**通过；六入口、19 模块与冻结源码/wheel/安装目录摘要一致。初始 183 项通过日志保留，补上等待附件重启用例后才记录最终 184 项。首次 fixture 混用了普通文件标记与文本，实际被正常阻断；修正为已有的引用文件结构后才得到上述竞态复现，不把错误 fixture 当产品缺陷。
