# 真实需求与项目边界

更新：2026-11-11。依据用户需求整理；验收方式与实现建议不等于已经验证的能力。执行计划见 [路线与工作清单](13-roadmap-and-backlog.md)。

## 要交付什么

让团队现有 Agent 经钉钉普通账号接入已授权的私聊、群聊，持续接收消息及附件，向正确会话回复文本和真实媒体，并使用钉钉组织内工具完成工作。沉淀成可供不同项目和服务复用的适配层、开通流程与证据库。

官方 DWS 是首选。先验证其实际覆盖，再决定适配层厚度；全部满足时交付纯 DWS 适配服务。macOS AX 仅作为具体缺口的候选补充，不能因为 WeCom 采用 AX 就照搬，也不能先假定钉钉和企微有相同限制。

## 为什么提出真实普通账号

用户补充：选择普通账号，出发点是避免平台原生 AI bot 的会话覆盖限制，特别是跨组织群、含外部成员的群、外部客户交流。用户以企微 bot 的接入限制作为已有经验，并明确对钉钉只是担忧其“可能”有类似限制，尚未作事实结论。

用户以 Slack/Telegram bot 作为易接入的参照，表达期望原生接口足够完整时可以直接使用。这里不将该参照表述为这些平台的 bot 没有权限、隐私或消息覆盖限制，也不需要为本项目证明海外平台完全无约束。

因此必须区分**业务覆盖要求**与**身份/实现手段**：当前按真实普通账号路线验证，原生 bot 同时作为能力对照；不能仅因接口丰富就用 bot 替代普通账号，也不能未调查便排除官方 bot。若某类 bot 在目标场景中确实等价满足要求，可列为实现候选，并明确它的独立身份及覆盖范围。是否需要 AX，取决于官方各路线实际剩余的缺口。

DWS 是工具入口，用户身份、应用机器人、自定义 webhook 是不同通道，不能合称“官方支持”后互相替代。账号能在客户端进入一个群，也不证明 DWS 获得该群事件或资源权限。

## 核心需求及验收含义

| ID | 需求 | 验收含义 |
|---|---|---|
| R01 | 普通账号进入现有会话 | 身份、组织、单聊/群聊目标唯一确定；不要求用户迁移到单独机器人会话；明确每次出站显示身份 |
| R02 | 私聊、群聊连续双向通信 | 另一成员的普通消息能进入 Agent；群聊不以 @ 为接收前提；回复进入原会话；各会话单独保存上下文 |
| R03 | 真实多媒体与文件 | 双向测试文本、纯图片、图文、文件、语音、视频；附件可落盘、打开或播放；文件校验名称、大小与摘要；媒体如发生平台转码，记录原件与下载件差异 |
| R04 | 持续运行和可恢复 | 进程重启、断线、补历史和重放不会产生无解释的缺失/重复；发送结果未知可查询对账；持续收消息不依赖一直打开该聊天窗口的人工操作 |
| R05 | 组织内工具 | Agent 能调用官方工具处理文档、待办、邮件、日程/会议等；逐项验证权限、真实写入与回读，不把命令存在当成功 |
| R06 | 通用工具与真实Agent接入 | bridge提供稳定事件、附件、发送接口；runtime可替换，同时至少本地Codex或Kimi完成真实多轮任务、文件交付与恢复验收 |
| R07 | 可复用、可交接 | 从管理员开通到运行排错都有步骤、版本、结果和证据；下一项目无需重新猜权限、身份、群类型和媒体限制 |

“接收到普通群消息”和“每条消息都自动回复”分别设计。接收覆盖是硬要求；自动响应条件由会话策略配置。建议第一版采用指定会话白名单、明确的群回复触发规则，以及自身消息过滤，防止循环回复。这是实施建议，不替用户决定业务回复策略。

音频文件以附件发送不自动算原生语音消息；视频链接不自动算视频回传；OCR/转写不替代原始图片/音频。若官方仅覆盖替代形态，应在矩阵中标为 partial，明确是否影响实际需求。

## 分层范围

**首个验证范围：** 单账号、单组织、当前指定群；随后加入一个明确允许测试的私聊。普通文本、所有核心媒体、历史读取与恢复均需要验证。文本 MVP 只是中间成果，不能作为整个项目完成标准。

**必须调查但分开验收：** 跨组织群、含外部成员的群、外部联系人/客户交流，是用户选择普通账号路线的重要原因，必须列入覆盖调查；加密资源、群成员与账号差异也需记录。当前没有专门的外部测试会话，不得将内部群成功扩大为全钉钉可用。缺少外部实测时只允许宣布“内部会话阶段通过”，不能宣布总体覆盖目标完成。企微对接个人微信客户是用户提供的比较场景，不假设钉钉存在一一对应的客户通道。

各类会话对 DWS 用户身份、应用 bot、自定义 webhook 分别回答：能否进入/被添加、能否读取普通非 @ 消息、能否查历史、能否收发每种原始媒体、能否主动发送、出站显示谁、管理员与组织边界、恢复机制。群类型按真实平台属性区分，不只靠“外部群”的口头名称。

**组织工具分批交付：** 文档与待办先做代表性闭环；邮件、日程、会议纪要及在线会议按独立能力验证。日程预约、会议纪要、创建实时音视频会议是不同功能；某项不可用就列为缺口，不用其他功能替代后声称完成。

**暂不作为第一版目标：** 全组织扫描、任意群自动加入、自动成员管理、多租户平台、全产品界面自动化、实时通话控制、全办公套件覆盖。后续需要时再扩展权限和范围。

## 官方优先如何落地

1. 以当前 CLI 版本 Help、官方资料及目标组织实测交叉验证。公开 issue 是测试线索，不是本组织永久限制。
2. 若事件、历史、原件和用户发送全通，采用 DWS + 小型持久化适配服务。
3. 若事件漏收而官方历史完整，测量有限范围补读是否能满足延迟要求；明确其为轮询补偿，并记录延迟。
4. 若某一能力仍缺失，先排查组织开通、OAuth scope、身份、群类型、版本和命令用法，再决定等待官方修复或探测 AX。
5. AX 只针对明确失败项做小实验。验证其可靠性、运行条件与维护成本后再纳入，不预先承诺 AX 能解决所有媒体/群限制。

即使 DWS 全通，仍需要会话路由、附件生命周期、事件去重、发送状态、进程恢复与 Agent 接口。bridge 的工作量取决于这些实测结果，不等于重写 DWS。

## 通用产品要求（用户本轮澄清）

本项目交付通用工具；测试账号/组织/群是验收样本，不是产品专属绑定。认证上下文和组织字段只用于正确访问/路由，不要求用户选择某个组织或Agent runtime作为开发前置。上层Agent保持可替换；提供CLI/HTTP公共接口、多账号多会话能力，并独立验收。用户最新明确还必须接入本机Codex或Kimi，实际在钉钉交办和完成任务；当前Kimi两轮闭环通过，见[docs/24](24-local-agent-product-and-acceptance.md)。

## 当前事实与未决项

已完成：独立知识库与本地 WeCom 实现对照；新组织管理员开通、认证和精确群绑定；单人文本/文件/新版内联图片 API 路径；本人文档/待办/日程/未发送草稿代表操作；多图客户端呈现；HTTP + SQLite 实验服务、重启幂等和停机补读验收；Kimi真实读取引用TXT、生成并回传报告、原生会话续接及gateway重启验收。

已补本轮 bot/用户身份逐格证据矩阵（docs/18），未知格子和验证路径保留。未完成：外部覆盖最终实测结论，实际普通消息入站覆盖、私聊/外部会话端到端、原生音视频、通用接入的完整实时能力和长期稳定性。多人现场测试按用户要求暂跳过，但文档调查继续。当前服务采用历史轮询，没有实现已验收的完整实时接收管线。文档进度与产品验收分开计，见 [总体复盘](17-requirements-progress-review.md)。

后续需要明确的产品参数包括：允许接入的会话范围、群回复触发方式、可接受延迟、离线恢复窗口、附件保留期、运行主机和长期账号。无需现在阻塞验证；在生产部署与扩大范围前形成明确配置。不得把未答复当成扩大监听范围的授权。

## 项目完成的判断

在约定账号、组织和会话类型内，R01–R07 各自有通过记录或用户接受的具体限制；任意符合公共契约的调用方可通过CLI/HTTP完成已验收通信与办公操作，保持runtime可替换，并有至少一个本地执行引擎的真实任务闭环；安装、启动、停止、故障恢复和重新接入可复现。对外说明附带版本与能力矩阵，不承诺全平台、所有群类型或 exactly-once 投递。
