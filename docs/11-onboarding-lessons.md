# 组织开通手册与已踩坑经验

适用于复用本项目的开发者、Agent 服务和后续组织接入。更新日期 2026-11-11；全局 DWS v1.0.61 保留，实验使用隔离 v1.0.67；钉钉 8.5.5 是此前本机检查快照。目标是让接入者先完成已知前置步骤，再验证消息能力，避免从安装命令重新踩一遍。

## 当前已走通的开通路径

1. 准备目标钉钉组织。本轮用户选择新建「深圳市弗忧智能科技」，成为管理员；**新建组织不是普遍必要条件**，已有合适组织也可接入。
2. **组织管理员必须在钉钉开发者平台手动开启 DWS/CLI 相关访问权限。**本轮由用户亲自完成并明确确认。仅安装 CLI、登录桌面端、创建组织或拥有管理员角色，不能替代这一步。
3. 官方 v1.0.67 README 明确路径：[开发者平台](https://open-dev.dingtalk.com) →「CLI 访问管理」→ 开启。未开通时登录流程也可申请、管理员卡片审批后再登录。人员可用范围按实际后台核对；本轮未独立点击后台，不把官方步骤冒充现场截图。
4. 用户通过 `dws auth login` 完成目标组织的 OAuth。管理员开通是组织层条件，用户 OAuth 是账号层条件，两者分别记录。
5. `dws auth status --format json` 必须检查 authenticated，而非只检查进程退出码。本轮开通前 exit=0 且 authenticated=false，后续复核为 true。
6. 用 `dws profile list --format json` 核对当前组织、账号及当前标记；当前实测为「深圳市弗忧智能科技有限公司 / 周威」。后续服务应绑定真实稳定 profile，不能依赖操作者上一次切换留下的默认值。
7. 在同一 profile 下查询唯一目标群，再分别验证历史读取、事件订阅、附件下载和发送。新组织默认群名称与组织全称相同，但它们不是同一个 ID。

第 1、2 步来自用户亲历确认；第 5、6 步有本机工具结果。管理员具体开通权限集合和 OAuth 本次操作顺序未被工具完整追踪；新群业务操作已另行逐项测试，不能把该路径写成全程自动化已通过。

## 前置状态必须分层

| 层次 | 当前证据 | 不能据此推出 |
|---|---|---|
| 组织存在、用户是管理员 | 用户确认 | CLI 已开启 |
| 管理员手动开通 | 用户确认完成 | 任意账号已登录、全部工具有权限 |
| 桌面客户端已登录 | 先前 AX 观察 | DWS 已登录同组织 |
| DWS 已认证 | AUTH-002 authenticated=true | 当前账号/组织一定正确 |
| 当前 profile 正确 | PROFILE-001 新组织/周威 | 群 ID、成员、群类别已确认 |
| 指定群订阅 ready | 新群短时启动与退出已测；他人入站跳过 | 真实消息一定到达 |
| 收到正文 | 新群本人发送历史回读通过；不是他人入站 | 原始附件可下载、出站可发送 |
| 本地发送气泡出现 | 旧组织 AX 冒烟 | 新组织通过、对端实收或已读 |

## 经验条目

### ONB-001 组织管理员手动开通是接入前置项

现象：安装 CLI 和桌面登录不足以完成组织数据接入。处理：先找目标组织管理员在开发者平台手动开通，再处理用户 OAuth。验收：分别保存管理员完成确认及当前 profile 认证结果。

复用要求：每一个新组织接入都检查这项；不要因另一个组织已开通而跳过。失败时先区分未开通、人员范围不含当前账号、OAuth 尚未完成以及具体业务权限不足，不凭一条错误猜根因。不要尝试靠反复重装 CLI 或换机器人凭据解决组织开通。

### ONB-002 桌面登录与 DWS 登录彼此独立

本轮曾同时出现桌面主界面可读、DWS authenticated=false。分别检查，不让用户在已经登录的桌面端重复扫码。当前 DWS 已成功认证，旧 false 仅保留为历史。

### ONB-003 切换组织必须重建目标绑定

当前联调由恒泰进 aic测试群切换到弗忧智能科技同名组织群。不得沿用旧 profile、群 ID、成员、订阅或测试结果。查询身份、解析会话、消费事件、下载、发送与订阅清理均使用同一 profile。

### ONB-004 退出码成功不等于业务成功

auth status 曾 exit=0 但 authenticated=false。资源查询也可能成功但下载台账失败。记录业务字段与数据完整性，不只看 shell 返回码。

### ONB-005 命令存在不代表服务端覆盖

本机 Help 有个人群事件、媒体发送参数，但外部群事件和加密媒体仍有上游问题证据。见能力矩阵。每个群、每种媒体逐项验证；ready、connected、active 都不能代替真实另一成员的入站消息。

### ONB-006 旧实验必须保留所属环境

DAB-AX-001 是恒泰进 aic测试群中的单次本地发送；不删除，也不重命名成新组织测试。后续结果带组织别名、群别名、软件版本、操作来源和验证级别。保持追加历史，另行更新当前状态。

### ONB-007 UI 会变化，旧元素序号不可复用

真实探测中用户改变界面后，工具拒绝旧动作；刷新后直接定位到用户已打开的测试群。以最新 AX 状态选控件，不重放过期坐标或序号。

### ONB-008 发送状态不明时不要切后端重发

官方超时不意味着未发送；AX 气泡出现也不是对端已读证明。使用共同投递账本并对账，防止官方发送与 AX 回退各发一次。

## 新项目或服务接入的最小交接包

- 固定 CLI、客户端版本及 Help 证据。
- 组织管理员开通完成记录、适用账号范围；原始后台截图如含身份应仅本地私存，不能存凭据。
- 本机私有配置中的稳定 profile 和 conversationId；文档只用必要别名。
- 目标群类别、成员及测试发件人，不凭名称猜。
- 已验证的能力矩阵及失败原因；保持 unknown，不用乐观默认值。
- 订阅启动/停止、实际消息到达、附件摘要、发送回执与清理记录。

上述未齐全时，将服务状态表述为“部分就绪”，明确缺项，不宣称完整 IM 闭环。

## 经验沉淀规则

每次踩坑至少记录：触发条件、版本与环境、可观察现象、已排除因素、采取步骤、验证结果、仍未知部分、下次直接复用的操作顺序。标明来源是用户亲历、工具实测、官方契约还是问题报告。

同时更新本页、人工清单、当前状态和实验记录；保存脱敏 evidence。不能只记成功步骤，也不能将未确认推断升级为平台永久限制。组织权限的确认不代表允许扩大到全部业务群。

证据：[新组织开通记录](../evidence/2026-11-10/new-org-onboarding.json)、[本机实验](07-local-results.md)、[官方接入说明](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/issues/1304#issuecomment-5761503069)。

## 2026-11-11 新经验

- ONB-009：群名搜索是模糊匹配，本轮返回默认群及带相同公司名的其他群。必须按精确名称、组织、群类别核对后绑定稳定 ID，不取第一项猜测。默认群 memberCount=1；按用户要求切换单人模式，不等待成员。
- ONB-010：同键同正文重复发送返回 exit=1、stderr JSON 中 CONFLICT_ERROR，stdout 为空。保存 exit/stdout/stderr，留存原任务 ID 对账；不能因 JSON 解析异常换 key 重发。
- ONB-011：v1.0.61 的 audio/video 参数是文件语义别名；PNG 本地发送也是 file。该v1.0.61基线下载摘要一致，但当时原生语音/视频/图片形态未通过；新版图片已另测。必须将文件可传输与原生形态分别验收。
- ONB-012：监听退出后本次订阅与消费者均消失，共享 bus 仍运行并显示 300 秒 idle timeout。不要因 bus 存在就判断订阅泄漏，也不要强杀可能被其他消费者复用的 bus。

来源均为本机 Help 与真实工具观察，详见 [单人报告](14-solo-test-report.md)。

## v1.0.67 与服务落地经验

- ONB-013：新版内联本地图片已可生成 mediaId，下载原图一致；旧版缺口要用隔离新版复测，不能据旧 Help 过早实施 AX。
- ONB-014：新版部分命令使用 ok/outcome/data 外层，其余保持专用 contract。仅识别确定外层解包，避免误吞业务 data 字段。
- ONB-015：桌面显示网络断开时，DWS 服务端发送、历史和办公操作仍成功。本轮不能验证桌面原生图片呈现；不要将桌面状态等同于 OAuth/API 状态。
- ONB-016：SQLite 发送保留先于外部副作用；服务重启不得重跑 executing，改标 outcome_unknown。独立进程锁、相同 key 内容约束和原任务对账已实现/测试。

见 [实现验收](16-implementation-acceptance.md) 与 [运行手册](15-service-runbook.md)。

## 新环境可复现顺序与版本差异

固定正式版本并校验 release SHA256 → 管理员开通 → 用户 OAuth → 核对 profile → 精确查询唯一目标会话 → 只读历史 → 约定单条合成发送 → 查询原任务状态 → 按消息 ID 下载并校验 → 验证事件真实到达及退出清理。先看 [复现手册](20-gap-acceptance-and-reproduction.md)，不要直接重放旧消息。

v1.0.67 常规监测可用 `auth status --readonly --format json --profile …`：只读本地认证快照，不刷新/迁移/抢认证锁；Keychain 读取仍可能等待。需要修复才去掉 readonly。v1.0.61 不支持此参数。来源：[固定版 README](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.67/README_zh.md)。本地快照通过不代表此刻远端业务调用一定通过。

- ONB-017：mail draft create 的邮件 ID 在 result.message.id；成功后必须按 ID 回读。没有收件人的草稿也可创建，本轮正文标记一致。不要因误取 messageId 字段为空而重复创建。
- ONB-018：calendar +create 即使没有指定在线会议，回读仍包含 onlineMeetingInfo 和默认提醒。日程、会议入口、实际入会分别记录；本轮是过去时段且仅本人。
- ONB-019：minutes 带测试 query 返回0且 complete=false，只证明该查询，不能写成账号无任何纪要。drive 对在线文档 +info 有元信息警告，不能算钉盘普通文件闭环。
- ONB-020：同一问题必须看群类型和版本。#937 后续评论未明确群类型，不照搬原报告；应用 bot 的同组织教程不等于全部智能机器人禁止外部群。

各模块实际通过范围和权限未知项见 [办公权限](19-office-tools-and-permissions.md)，身份与外部会话见 [边界矩阵](18-identity-and-conversation-boundaries.md)。

- ONB-021：send文本用--text、reply正文用--content。错误旗标在解析阶段exit=3并未提交任务；保留错误证据后修正参数，沿用原key。服务把success的false和字符串"false"都当失败；缺senderId保持未知，防止self-loop。

## 本地 Agent 接入经验

- ONB-022：Codex CLI已登录不等于模型调用成功。0.164.0两次实际请求分别在120/90秒内超时；Kimi 2.1.1能实际执行，因此先交付Kimi闭环，Codex如实留待验收。
- ONB-023：Kimi 2.1.1的prompt模式不能与yolo/auto旗标组合，prompt自身使用auto权限。移除冲突旗标后完成实际文件任务；不能把无人工弹窗误称为OS隔离。
- ONB-024：Kimi JSONL末尾session.resume_hint提供精确会话ID；本机观察到末尾事件后CLI可能仍持有句柄。保存结果后只结束本次owned进程组；两轮实际session一致、第二轮无工具即记起代号，验证了恢复有效。
- ONB-025：单人普通账号需要明确owner-command模式验证真实runtime；授权sender+显式前缀，与普通本人消息/Agent回声过滤分开。不要为方便而全局关闭self过滤，也不将其记成独立对端入站成功。
- ONB-026：执行幂等和消息幂等分别持久化。工具执行被打断不能因重启自动重做；消息回包丢失复用同一发送键对账。完整重启验收比较任务、会话、执行日志和outbox。

来源与复现：[实际接入记录](24-local-agent-product-and-acceptance.md)、[Kimi命令契约](https://moonshotai.github.io/kimi-code/en/reference/kimi-command.html)、[脱敏验收](../evidence/2026-11-11/local-agent-loop.json)。

- ONB-027：DWS v1.0.67已有dev connect本地机器人Agent接入，应先纳入选型；用户身份与bot身份不同，不能以其中一条的能力代替另一条。
- ONB-028：官方流式文本卡片返回success/accepted不等于内容verified；本轮明确verified=false且缺少完整引用对，不盲目重复更新以试探。
- ONB-029：子进程测试发现末行无换行丢失、stdin阻塞取消及macOS退出信号竞争；修复后分别验证，不拿CLI参数列表代替运行时测试。
- ONB-030：同步下载附件会阻塞控制消息；改为单个后台只读请求、主线程落账后，用阻塞下载故障测试及真实图片任务验证。

详见[官方边界与场景台账](25-official-boundary-and-scenarios.md)。
